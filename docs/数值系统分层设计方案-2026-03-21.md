# 数值系统分层设计方案

日期：2026-03-21

## 1. 目标与问题

你当前要解决的是三个核心问题：

1. `好感度/心情值` 由谁存储（Nanobot/未来 Agent 框架，还是软件本体）。
2. 数值如何变化（谁来判定、如何防止失控、如何解释变化）。
3. 未来接入“快速模型层”后，如何与现有推理后端（Nanobot/其他 Agent）协同。

本方案的目标是：

1. 保证后端可替换，不锁死任何单一 Agent 框架。
2. 保证数值连续、可控、可审计。
3. 支持后续扩展更多数值（信任、压力、活力等）且不返工。

## 2. 核心结论

### 2.1 存储归属

`好感度/心情值` 的最终存储和最终裁决，放在软件本体（Electron 主进程）中，不放在 Nanobot 或未来 Agent 框架中。

### 2.2 判定归属

采用“`AI建议 + 软件裁决`”双层机制：

1. Agent/模型只输出“建议变化量”（delta），不能直接写最终值。
2. 软件规则引擎做二次裁决（限幅、冷却、去重、异常拦截）。
3. 主进程持久化最终结果，并写入事件日志。

### 2.3 快速模型层定位

快速模型层应当负责：

1. 快速回复（低延迟对答兜底）。
2. 数值变化建议生成（mood/affinity deltas）。
3. 轻量情绪/意图识别。

快速模型层不应当负责最终状态写入；唯一状态真相源仍是软件本体。

## 3. 架构建议（分层）

建议采用四层：

1. `UI层（Renderer）`
2. `状态与规则层（Electron Main，唯一真相源 SoT）`
3. `快速模型层（Fast Model Layer）`
4. `推理后端层（Nanobot / future agents）`

职责如下：

1. UI层：展示当前数值、变化提示、历史摘要。
2. 状态与规则层：读取/写入数值、规则裁决、反刷、审计日志、向模型注入状态摘要。
3. 快速模型层：快速产出应答和 delta 建议。
4. 推理后端层：复杂推理、工具调用、长链任务；可附带 delta 建议。

## 5. 数值变化机制

### 5.1 总原则

1. 模型只给“增量建议”，不允许设置绝对值。
2. 每回合有变化上限（turn cap）。
3. 短期值与长期值分离：
   - 心情值 `mood`：短周期、波动快、可自动回归基线。
   - 好感度 `affinity`：长期累计、变化慢、抗噪声。

### 5.2 建议范围与节奏

1. `mood`: `[-100, 100]`，单回合建议上限 `±8`。
2. `affinity`: `[0, 1000]`，单回合建议上限 `±3`。
3. 回归机制：每若干回合将 `mood` 向 `baseline` 回归（如每回合 ±1 回归）。
4. 稀释机制：同类事件短时间重复触发时，增益递减（防刷分）。

### 5.3 触发来源

三类触发可并存：

1. 规则触发（确定性）：
   - 命中关键词/显式行为事件，直接给默认增减建议。
2. AI触发（语义）：
   - 由快速模型或推理模型输出 delta 建议。
3. 系统触发：
   - 长时间无交互、任务失败/超时、连续打断等系统事件。

最终进入统一裁决管道。

## 6. 提示词与模型输出协议

### 6.1 推荐协议（强约束 JSON）

模型返回示例：

```json
{
  "stat_updates": [
    {
      "stat": "mood",
      "delta": 4,
      "reason": "用户表达赞赏，语气积极",
      "confidence": 0.82,
      "tags": ["praise", "positive"]
    },
    {
      "stat": "affinity",
      "delta": 1,
      "reason": "用户主动建立长期协作意愿",
      "confidence": 0.74,
      "tags": ["trust_building"]
    }
  ]
}
```

约束要点：

1. 仅允许输出白名单 `stat`。
2. `delta` 必须是整数，且在允许范围内。
3. 必须提供 `reason` 和 `confidence`。
4. 若无变化，返回空数组，不输出自由文本。

### 6.2 规则引擎二次裁决（必须）

主进程在落库前执行：

1. schema 校验。
2. 上下限与单回合限幅。
3. 冷却窗口检查（同标签短时重复衰减）。
4. 异常拦截（低置信度、矛盾建议、恶意注入）。

## 7. 为什么不把主存储放到 Nanobot/Agent 框架

1. 未来你会接入多个框架，状态不应与某一框架耦合。
2. 你需要在后端切换时保持同一角色数值连续。
3. 本地主进程更适合执行安全规则与审计。
4. 框架可选地缓存镜像，但镜像不是权威数据。

## 8. 与“快速模型层”结合方案

### 8.1 快速层触发时机

1. 用户输入到达后，先走快速层得到：
   - 低延迟文本回应（可选）
   - 数值建议
2. 推理后端结果返回后，再进行：
   - 结果对齐（可二次建议）
   - 必要时补偿修正（仍经主进程裁决）

### 8.2 冲突处理

当快速层与推理层建议冲突时：

1. 以规则引擎权重合并：`finalDelta = weightedBlend + clamp`。
2. 高置信度且与用户显式行为一致的建议优先。
3. 推理层若无明确建议，不阻塞快速层的数值更新。

## 9. 在当前仓库的落地建议（最小侵入）

建议新增/改造模块：

1. `desktop/electron/services/valueState/valueStateStore.js`
2. `desktop/electron/services/valueState/valueRuleEngine.js`
3. `desktop/electron/services/valueState/valueProposalService.js`
4. `desktop/electron/ipc/valueState.js`
5. `desktop/electron/preload.js`：暴露 `valueState` 只读/订阅/手动刷新接口
6. `front_end/src/services/desktopBridge.js`：补充 value-state bridge

与现有对话链路集成点：

1. `conversationRuntime` 在每回合结束后触发 `proposal -> rule -> commit`。
2. `conversation:event` 增加数值变化事件（如 `channel: system`, `type: stat-updated`）。
3. 向模型注入“状态摘要”时只传必要最小信息，避免泄露完整历史。

## 10. 分阶段实施计划

### Phase 1（先稳定）

1. 建立本地主进程状态存储与日志。
2. 接入纯规则版增减（不依赖模型建议）。
3. 前端显示当前数值和最近一次变化。

### Phase 2（引入 AI 建议）

1. 增加结构化 `stat_updates` 协议。
2. 接入规则引擎二次裁决。
3. 做反刷与冷却策略。

### Phase 3（接入快速模型层）

1. 快速层加入意图/情绪识别与 delta 建议。
2. 与推理层做冲突合并。
3. 完成回归测试与参数调优。

### Phase 4（可扩展）

1. 扩展更多 stat（信任、依赖、疲劳等）。
2. 把 stat 定义改为配置化（元数据驱动）。
3. 加入可视化调参面板（仅开发者模式）。

## 11. 测试建议

重点覆盖：

1. 规则引擎限幅、下上限、回归、冷却逻辑。
2. 同回合多来源建议合并与冲突处理。
3. 异常 JSON/注入文本容错。
4. 后端切换（Nanobot -> 其他 Agent）后数值连续性。
5. 应用重启后状态与日志恢复。

## 12. 最终建议（可执行）

你提出的方向里，“让 AI 参与判定”是非常对的，但建议升级为：

1. `AI 负责建议`。
2. `软件本体负责裁决与存储`。
3. `快速模型层负责低延迟与数值管理协同`。

这样既保留角色拟人化的灵活性，也能保证系统长期稳定、可扩展、可审计。
