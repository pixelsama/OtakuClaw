# 静态高清角色形象接入规划（Live2D 之外的第二方案）

更新时间：2026-03-24  
适用分支：`codex/e59c`

## 1. 背景与目标

当前角色渲染能力主要依赖 Live2D。为了给用户提供更低门槛、更高画质、更易自定义的方案，本规划新增“静态图片为主”的角色形象能力，与 Live2D 并存。

核心目标：

1. 用户可导入静态角色资源包（ZIP），并在主窗口/桌宠/沉浸视图中使用。
2. 维持现有交互体验（拖拽、缩放、基本视线跟随、语音口型最小反馈）。
3. 不破坏现有 Live2D 路径，支持随时切换回 Live2D。
4. 保持 Electron 安全边界与资源路径隔离。

## 2. 范围定义

### 2.1 In Scope（首版）

1. 渲染模式切换：`live2d | static`。
2. 静态资源包导入、列表、选择、删除（可选）能力。
3. 静态角色基础状态：`idle/writing/researching/executing/error`。
4. 可选口型帧：`talk_0..talk_n`（无则回退 idle）。
5. 桌宠拖拽命中（支持透明像素命中或矩形命中回退）。
6. 角色缩放、位置同步、窗口模式兼容。

### 2.2 Out of Scope（首版不做）

1. 复杂骨骼动画与物理模拟。
2. PSD 分层编辑器与在线素材市场。
3. 多角色同时上屏的完整编排系统。
4. 资源包云同步。

## 3. 方案概览

采用“渲染器抽象 + 资源包契约 + 双栈并存”的路线：

1. 在前端抽象统一 `AvatarRenderer` 接口，封装 `Live2DViewer` 与 `StaticAvatarViewer`。
2. 主进程新增 `StaticAvatarLibrary`，复用现有 ZIP 导入与协议映射模式。
3. 新增 `static-avatar` 资源契约（manifest + assets）。
4. 设置项新增 `ui.avatar`，用于保存渲染模式与已选资源。

## 4. 资源包契约（建议 v1）

文件结构：

```text
<avatar-pack>.zip
  manifest.json
  assets/
    character/
      idle.webp
      writing.webp
      researching.webp
      executing.webp
      error.webp
      talk_0.webp
      talk_1.webp
```

`manifest.json` 建议字段：

```json
{
  "schemaVersion": 1,
  "packId": "com.otakuclaw.avatar.demo",
  "name": "Demo Static Avatar",
  "version": "1.0.0",
  "engine": ">=0.3.0",
  "states": {
    "idle": "assets/character/idle.webp",
    "writing": "assets/character/writing.webp",
    "researching": "assets/character/researching.webp",
    "executing": "assets/character/executing.webp",
    "error": "assets/character/error.webp"
  },
  "talkFrames": [
    "assets/character/talk_0.webp",
    "assets/character/talk_1.webp"
  ],
  "hitTest": {
    "mode": "alpha",
    "alphaThreshold": 10
  }
}
```

校验规则：

1. manifest 必须存在且可解析。
2. `schemaVersion` 必须匹配。
3. 所有路径必须在 ZIP 内，拒绝路径穿越。
4. 素材 MIME 与扩展名白名单（`png/jpg/jpeg/webp/avif`）。
5. 限制单文件大小与总包大小（防止资源炸弹）。

## 6. 统一渲染接口（关键）

`AvatarRenderer` 对外暴露统一方法（至少）：

1. `isPointOnModel(x, y, alphaThreshold?)`
2. `setPointerNormalized(nx, ny)`
3. `syncCanvasSize()`
4. `getManager()`（可返回轻量 manager，保持兼容）

目的：尽量不改动桌宠拖拽、鼠标穿透和现有壳层逻辑。

## 7. 分阶段计划

### Phase 0（0.5 天）设计冻结

1. 确认 manifest v1 字段。
2. 确认渲染接口兼容边界。
3. 出最小测试矩阵。

验收：

1. 设计评审通过。

### Phase 1（1-2 天）前端渲染打底

1. 实现 `StaticAvatarViewer`（本地假数据）。
2. 接入 `AvatarRenderer`，不改主进程导入。
3. 主窗口+桌宠完成静态渲染切换。

验收：

1. 模式切换稳定。
2. 桌宠可拖拽、可缩放。

### Phase 2（1-2 天）主进程资源库接入

1. 完成 `staticAvatars` IPC + library。
2. ZIP 导入/列出/选择流程打通。
3. 设置持久化联动。

验收：

1. 重启后仍能恢复静态角色。
2. 非法包可被拒绝并提示原因。

### Phase 3（1 天）交互增强与回归

1. 语音播放时启用 talk 帧循环（无帧则不启用）。
2. 增加状态映射（businessState -> static frame）。
3. 完成桌宠命中判定回归与窗口模式回归。

验收：

1. 语音时角色有最小动态反馈。
2. 状态切换不闪烁、不丢帧。

## 8. 测试计划

桌面端（`pnpm run test:desktop`）新增：

1. `staticAvatarLibrary` 导入、解析、路径穿越拒绝。
2. `static-avatars:*` IPC 返回与错误映射。

前端（`pnpm run test:frontend`）新增：

1. `AvatarRenderer` 在 `live2d/static` 下渲染切换。
2. `PetShell` 命中判定兼容（静态模式）。
3. 配置面板模式切换与持久化恢复。

手工回归：

1. 主窗口 / 桌宠 / 沉浸模式一致性。
2. 语音中断与快速切换模型稳定性。

## 9. 风险与缓解

1. 高清图显存占用高。  
   缓解：限制尺寸、限制帧数、分辨率分档。
2. 静态图交互感不及 Live2D。  
   缓解：先补口型帧与轻微视差，明确产品预期。
3. 导入包安全风险。  
   缓解：严格路径与 MIME 校验、大小上限、失败回退。

## 10. 交付定义（MVP）

满足以下条件即视为 MVP 完成：

1. 用户可导入静态角色 ZIP 并启用。
2. 主窗口、桌宠模式可显示静态角色。
3. 角色状态可随业务态切换。
4. 重启后配置可恢复。
5. 不影响 Live2D 原流程。
