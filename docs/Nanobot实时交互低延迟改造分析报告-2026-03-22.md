# Nanobot 实时交互低延迟改造分析报告

日期：2026-03-22

## 1. 目的

本文档用于梳理当前仓库中，围绕 `Nanobot` 聊天链路已经落地的“降低回复延迟 / 降低体感等待”相关改造措施，并明确这些措施分别落在：

1. 提示词与行为约束
2. 中间态事件输出
3. 前后端事件过滤与展示
4. 运行时复用与启动成本控制

本文档只描述当前代码里已经能确认的实现，不把未来规划或设计草案混入现状结论。

## 2. 结论摘要

当前项目并没有实现一个独立的“快速反应层模型 + 专用推理后端模型”的双层编排系统。

当前实际落地的是：

1. 仍然以单个 `Nanobot Agent` 为核心执行体。
2. 通过 patch `Nanobot` 的 identity/system prompt，强制加入桌面实时对话指导。
3. 利用 `Nanobot` 的 `on_progress` 回调提前输出中间态回复，而不是只等待最终答案。
4. 在 Electron 侧把中间态包装成用户可见的短回复，并把内部工具痕迹隐藏起来。
5. 通过 bridge 常驻、agent 复用、默认裁剪高风险工具等方式，尽量压低冷启动与执行过程中的体感延迟。

换句话说，当前方案不是“多层模型协同降延迟”，而是“单个 Nanobot + prompt/bridge/UI 适配”。

## 3. 已落地的低延迟改造措施

### 3.1 Patch ContextBuilder，把桌面实时对话指导注入 identity/system prompt

文件：

- `desktop/electron/services/chat/nanobot/nanobot_bridge.py`

核心实现：

1. 定义了 `DESKTOP_REALTIME_GUIDANCE`。
2. 通过 patch `ContextBuilder._get_identity()` 把这段 guidance 追加到 Nanobot identity 中。

对应代码位置：

- `DESKTOP_REALTIME_GUIDANCE` 定义：
  - `desktop/electron/services/chat/nanobot/nanobot_bridge.py:42`
- patch identity：
  - `desktop/electron/services/chat/nanobot/nanobot_bridge.py:203`

这段 guidance 的实时交互导向非常明确，核心要求包括：

1. 当用户请求可能需要工具调用或多步处理时，通常先给用户一句简短自然的回复。
2. 第一条回复要像口语对话，简短，保持角色感。
3. 不要在用户可见进度回复里暴露内部推理、工具名、函数语法、文件路径、执行细节。
4. 如果发送进度式回复，要保持简短、温和、面向用户。
5. 输出必须适合直接 TTS 播放，避免 Markdown、链接、命令、路径、JSON、代码片段等。

这说明当前系统确实通过修改 prompt/identity 来引导 Nanobot：

1. 更早开口
2. 先给一句短回复
3. 避免把等待过程表现成“沉默”
4. 避免输出不适合实时语音播放的内容

这是一项非常明确的“降低体感等待时间”改造。

### 3.2 接入 Nanobot 的 on_progress 回调，提前产出中间态回复

文件：

- `desktop/electron/services/chat/nanobot/nanobot_bridge.py`

核心实现：

1. 在 `handle_start(...)` 中调用 `agent._process_message(...)`。
2. 显式传入 `on_progress=on_progress`。

对应代码位置：

- `handle_start`：
  - `desktop/electron/services/chat/nanobot/nanobot_bridge.py:481`
- `on_progress` 定义：
  - `desktop/electron/services/chat/nanobot/nanobot_bridge.py:502`
- `_process_message(..., on_progress=on_progress)`：
  - `desktop/electron/services/chat/nanobot/nanobot_bridge.py:543`

这意味着当前桥接层不是“阻塞到最终回答后一次性返回”，而是允许 Nanobot 在执行过程中不断抛出中间进度。

中间进度目前分两类：

1. `tool_hint`
   - 用于表达当前工具调用方向
2. `progress`
   - 用于表达用户可见的中间回复文本

对应发射逻辑：

- `tool-hint` 输出：
  - `desktop/electron/services/chat/nanobot/nanobot_bridge.py:505`
- `progress` 输出：
  - `desktop/electron/services/chat/nanobot/nanobot_bridge.py:524`

从实时交互角度看，这一改造的意义是：

1. 用户更早收到反馈
2. 工具调用前不需要完全沉默
3. 前端字幕和 TTS 可以更早开始显示/播报

### 3.3 只取第一块可见 progress，过滤掉内部 thinking 块

文件：

- `desktop/electron/services/chat/nanobot/nanobot_bridge.py`

核心实现：

1. `first_progress_block(content)` 会把 progress 文本按空行拆块。
2. 只取第一块作为用户可见进度。
3. 如果第一块以 `Thinking [` 开头，直接丢弃。

对应代码位置：

- `first_progress_block`：
  - `desktop/electron/services/chat/nanobot/nanobot_bridge.py:466`

这说明桥接层在主动做“进度文本瘦身”：

1. 不把 Nanobot 原始完整 progress 全量暴露给 UI
2. 优先保留第一句、第一块，更像实时陪伴中的口语过渡
3. 直接隐藏带有明显内部推理味道的 `thinking` 块

这会降低用户看到冗长中间态的概率，也更有利于尽早给出简短反馈。

### 3.4 前端适配层把 progress 当成 text-delta 先显示，减少等待感

文件：

- `desktop/electron/services/chat/backends/nanobotBackend.js`

核心实现：

1. 后端收到 `progress` 事件后，不保留一个单独的“进度事件语义”给上层 UI。
2. 而是把 `progress` 统一转成 `text-delta`。

对应代码位置：

- 识别 `progress` / `text-delta`：
  - `desktop/electron/services/chat/backends/nanobotBackend.js:318`
- 转发时把 `progress` 改成 `text-delta`：
  - `desktop/electron/services/chat/backends/nanobotBackend.js:361`

这意味着对现有前端字幕链路而言：

1. 不需要新增一套“进度展示通道”
2. 中间进度可以像普通流式回复一样，直接进入字幕、消息增量、后续 TTS 流程

这是一个非常实用的低侵入优化：既提前显示内容，又不需要重构现有 UI 消费协议。

### 3.5 去重与增量切片，避免 progress 和 final reply 重复显示

2. 如果最终答案覆盖了前面 progress 已经显示的内容，只补发“新增的那一段”。

对应代码位置：

- 重叠切片函数：
  - `desktop/electron/services/chat/backends/nanobotBackend.js:137`
- 计算 incremental content：
  - `desktop/electron/services/chat/backends/nanobotBackend.js:343`

这样做的目的不是缩短模型真实推理时间，而是缩短用户的“无效等待感”和“重复阅读负担”：

1. 中间态可以先展示
2. 最终态来了不会把前面那段再说一遍
3. UI 看起来更连续、更像流式实时响应

### 3.6 工具提示和工具调用痕迹不直接展示给用户

核心实现分两层：

1. `tool-hint` 不显示给用户，改造成 `agent-state`
2. 文本中的工具调用痕迹会被清洗掉，只保留对用户自然的正文

对应代码位置：

- `tool-hint` 转 `agent-state`：
  - `desktop/electron/services/chat/backends/nanobotBackend.js:295`
- 工具活动映射表：
  - `desktop/electron/services/chat/backends/nanobotBackend.js:78`
- 清洗工具调用行：
  - `desktop/electron/services/chat/backends/nanobotBackend.js:113`

这样做的低延迟价值在于：

2. 用户先收到“我先帮你看看”这种自然语言，而不是 `read_file(...)`
3. 像素办公室可以立刻进入 `researching` / `executing`，而聊天区仍保持角色化表达

这类改造本质是在优化“实时反馈质量”。

### 3.7 默认裁剪高风险工具，缩小工具空间

- `desktop/electron/services/chat/nanobot/nanobot_bridge.py`

核心实现：

1. `exec`
2. `spawn`
3. `web_search`
4. `web_fetch`
5. `cron`

对应代码位置：

  - `desktop/electron/services/chat/nanobot/nanobot_bridge.py:429`

1. 减少 agent 可选动作集合
2. 减少走复杂外部执行分支的概率
3. 更容易留在“本地文件 / 本地上下文 / 简短回复”路径上

这不是一个纯粹为了 TTFT 的优化，但它确实会影响平均交互节奏。

## 5. 当前没有看到的能力

基于本轮代码检查，当前没有看到以下能力已经实现：

### 5.1 没有独立的快速模型层

没有看到一个单独的“快回复模型”先生成首句，再把复杂推理交给另一个后端。

当前仍然是一个 `Nanobot Agent` 在跑，只是被 prompt 和 bridge 适配成更适合实时对话。

### 5.2 没有本地生成中间安抚语句

没有看到 Electron 侧或 bridge 侧自己生成诸如“我先看看喵”这一类兜底短句。

当前中间态文本依然主要依赖：

1. prompt 引导
2. Nanobot 自身在 `on_progress` 中吐出内容

### 5.3 没有看到更重型的系统级低延迟优化

目前没看到这些内容已经落地：

1. prompt cache
2. speculative decoding
3. 预热独立快模型
4. 双通道路由器
5. 首 token 专门监控与动态降级策略

当前优化重心更偏：

1. 让用户更早看到一句自然回复
2. 让中间态更像“对话中的陪伴反馈”
3. 减少冷启动和重复内容

## 6. 总结

当前仓库为了让 `Nanobot` 更适合实时交互，已经做了较明确的定制化改造，主要集中在四个层面：

1. `Prompt/Identity` 层：
   - 强制注入桌面实时对话规则，要求先给短回复、隐藏内部细节、适配 TTS。
2. `Bridge` 层：
   - 接入 `on_progress`，把中间态及时抛出；过滤 `thinking` 风格进度；复用 agent；保持 bridge 常驻。
3. `Backend adapter` 层：
   - 把 progress 转成 `text-delta`；裁掉工具痕迹；把 tool hint 变成 activity；做重叠去重。
4. `Runtime policy` 层：
   - 默认裁剪高风险工具，减少复杂执行路径。

因此，当前系统已经具备明显的“实时化 Nanobot 适配”特征。

但它仍然不是一个“快层模型 + 慢层推理模型”的双层结构，而是单个 `Nanobot Agent` 在桌宠场景下做了 prompt、事件、展示、运行时上的多处低延迟优化。
