# AI 实机回归自动化路线图（未来更新方向）

> 日期：2026-03-21
> 状态：规划中（未实施）

## 1. 背景
随着桌面端功能持续增加（语音会话、模型下载/安装、运行时管理、窗口模式切换、截图链路等），旧功能的使用路径正在被新逻辑改写。仅依赖单元测试和局部手测，难以及时发现跨模块回归、低频异常路径和破坏性操作带来的崩溃风险。

## 2. 目标
1. 建立“可长期运行”的 AI 驱动实机回归体系，覆盖大多数真实使用场景。
2. 系统化覆盖低频但高风险的破坏性操作，验证“不会崩溃、能恢复、状态一致”。
3. 形成可重复、可追踪、可比较的自动化报告，支持 PR 阶段、夜间回归和长稳测试。

## 3. 非目标
1. 不追求一次性 100% 覆盖全部 UI 分支。
2. 不让 AI 直接替代所有断言逻辑（核心断言仍由规则化检查器完成）。
3. 不在首期引入大规模视觉识别模型流水线（先用 CDP + 结构化断言）。

## 4. 总体方案（分层）

### 4.1 场景层（Scenario DSL）
以 `yaml/json` 定义场景，包含：
- 前置条件（重置数据、启动参数、模型状态）
- 操作步骤（点击、输入、切换、等待）
- 断言（UI 文案、按钮状态、进度阶段、IPC 事件）
- 注入点（中断、重启、并发、取消、异常输入）

### 4.2 执行层（Real Device Driver）
基于已安装 App + CDP 实机操作：
- 启动：`open -a "/Applications/OtakuClaw.app" --args --remote-debugging-port=9222`
- 控件策略：优先 role/label 文本定位，避免依赖易变 id
- 支持重试与超时保护，避免单步阻塞拖垮整条流水线

### 4.3 观测层（Oracles）
多源校验避免“看起来成功但实际失败”：
- UI 层：状态文本、进度、按钮可用性
- 事件层：关键 IPC 事件序列
- 进程层：崩溃/退出码/卡死超时
- 文件层：状态文件与模型落盘一致性

### 4.4 破坏注入层（Chaos Hooks）
在关键阶段注入异常行为：
- 下载中取消/重试/重复触发
- 安装中切换模型、切换后端、切换窗口模式
- 安装进行中强杀 App 并重启恢复
- 语音播放中 pause/resume/stop 与新请求交错
- 非法输入与边界输入（空值、超长、重复提交）

### 4.5 报告层（Artifacts）
统一输出到 `/tmp/openclaw-gui-test/`：
- `full-flow-report.json`（结构化结果）
- `cdp_full_flow.log`（执行日志）
- 关键截图（失败点前后）
- 场景时间线（步骤耗时、失败定位、根因标签）

## 5. 场景覆盖优先级

### P0（首批必须）
1. 首次启动完整引导（Nanobot runtime + ASR + TTS 下载）
2. 语音会话主链路（start -> asr-final -> chat -> tts）
3. 语音下载任务取消/重试/恢复
4. 模型切换与 runtime warmup 稳定性

### P1（高价值低频）
1. 下载中切换窗口模式（window/pet）
2. 下载中切换后端（openclaw/nanobot）
3. 删除当前已选模型并立即触发对话/语音
4. 截图权限拒绝后的回退路径

### P2（破坏性与长稳）
1. 安装中强杀进程并重启恢复
2. 连续高频操作 30~60 分钟无崩溃（soak）
3. 多任务交错下状态一致性验证

## 6. 工作流设计
1. PR 快速实机回归（10~15 分钟）
   - 仅跑 P0 精简子集，作为合并前信号
2. Nightly 全量回归（60~120 分钟）
   - 跑 P0 + P1 + 部分 P2
3. Weekly 长稳回归（4~8 小时）
   - 长时间交互、并发与恢复场景

## 7. MVP 实施计划（建议两周）

### 阶段 A：基础框架
1. 新建 `docs/scripts` 对应的 scenario runner
2. 统一步骤执行器与断言器
3. 落地报告格式和失败截图

### 阶段 B：场景首批落地
1. 先实现 8 条高价值场景（含 3 条破坏性）
2. 接入已有脚本能力（例如 `docs/scripts/cdp_wait_model_download_done.js`）
3. 输出 nightly 报告样例

### 阶段 C：CI 与门禁
1. 接入 macOS 自托管 runner
2. 新增 nightly workflow
3. PR 快速回归做为非阻塞告警，稳定后升级为阻塞门禁

## 8. 验收标准
1. P0 场景通过率 >= 95%（7 日滚动）
2. 崩溃率显著下降，且新增崩溃可在报告中定位到具体步骤
3. 关键失败均具备“复现步骤 + 失败截图 + 根因标签”
4. 对“取消/恢复/重试/重启恢复”路径有稳定自动化覆盖

## 9. 风险与应对
1. UI 结构变更导致脚本脆弱
   - 应对：统一 Locator 规范，优先语义定位，弱化硬编码选择器
2. 实机环境波动导致假阳性
   - 应对：分层超时、重试、隔离网络波动标记
3. 运行成本较高
   - 应对：PR 跑精简集，重负载场景放到 nightly/weekly

## 10. 后续扩展
1. 引入“风险热区”自动选测：按近期改动文件映射场景优先级
2. 引入故障聚类：自动把同类失败归并为单一问题簇
3. 增加性能阈值门禁：首音延迟、下载耗时、恢复耗时的回归告警
