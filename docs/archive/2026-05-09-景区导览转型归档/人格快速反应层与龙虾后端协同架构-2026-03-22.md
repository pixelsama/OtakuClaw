# 人格快速反应层与龙虾后端协同架构

日期：2026-03-22

## 1. 背景

当前项目的产品定位，不是再造一个更强的通用 Agent 框架，而是为现有 `claw` 类开源 Agent 提供一个具有情绪价值与陪伴感的壳：

1. 像素房间
2. AI 少女角色
3. mood / affinity 数值
4. 桌宠与沉浸式互动
5. 与现有 `Nanobot / OpenClaw / future claws` 的对接

这意味着项目的核心价值不在“谁更会调工具”，而在：

1. 用户是否感觉这个角色是连续存在的
2. 用户是否能感受到人格与关系的积累
3. 用户是否能在日常轻量交互中获得低延迟、自然的陪伴反馈

在此前讨论中，围绕“快速反应层、长期记忆、后端龙虾框架的关系”形成了若干方案。本文档用于收敛出当前最适合本项目定位的一版。

## 2. 核心结论

当前推荐架构不是：

1. 自己完整实现一套独立长期记忆系统，再要求后端龙虾全面配合
2. 或者完全把人格、记忆、表达都交给后端龙虾

而是采用一种更轻、更符合“壳”定位的方案：

### 2.1 架构主张

项目采用：

1. `人格快速反应层`
2. `龙虾后端能力层`

两层协同，但边界清晰。

### 2.2 快速反应层负责什么

快速反应层负责：

1. 角色人格 prompt
2. mood / affinity 与角色状态
3. 极轻量短期记忆
4. 首句快速回复
5. 是否升级到后端龙虾处理
6. 最终输出的人格化包装

### 2.3 龙虾后端负责什么

龙虾后端负责：

1. 长期任务记忆
2. 工具调用与 agent loop
3. 搜索 / 文件 / 执行 / 工作流
4. 更重的推理链路
5. 框架原生长期记忆与上下文能力

### 2.4 对“记忆”的最终态度

当前不建议在壳层自己实现一套完整长期记忆框架。

当前建议：

1. 壳层拥有 `短期记忆 + 人格状态`
2. 龙虾后端继续拥有 `更丰富的长期记忆`
3. 当短期记忆不足时，升级到龙虾
4. 龙虾返回的更强记忆结果再回流进入当前上下文

一句话概括：

`快速反应层 = 人格 prompt + 短期记忆文件 + 自动压缩 + 升级判断`

其余复杂记忆能力交给龙虾后端。

## 3. 为什么这版方案最适合当前项目

### 3.1 保持“壳”的定位

如果壳层自己实现：

1. relationship memory store
2. 记忆蒸馏
3. 记忆投影
4. 检索与排序
5. 长期持久化记忆框架

那么这个项目就会从“给现有 Agent 增加情绪价值的壳”，逐渐滑向“自己造一个半独立 Agent 框架”。

这会显著提高：

1. 实现复杂度
2. 维护成本
3. 与后端 Agent 框架的冲突风险

### 3.2 保留后端龙虾的核心价值

`Nanobot / OpenClaw / future claws` 真正值得复用的，不只是工具能力，还包括：

1. 成熟的 agent loop
2. 任务工作记忆
3. 上下文窗口管理
4. 工具调度与回退机制

如果壳层强行接管全部记忆，容易削弱这些框架被采用的意义。

### 3.3 同时满足“情绪价值”和“低延迟”

绝大多数陪伴型交互并不需要每次都走完整的龙虾推理链路。

很多时候用户只是在：

1. 打招呼
2. 闲聊
3. 观察角色状态
4. 做轻量互动

这类请求更适合由一个轻量人格快速层直接处理：

1. 延迟更低
2. 成本更低
3. 角色连续性感更强

而一旦需要：

1. 回忆更复杂的旧信息
2. 调工具
3. 做明确任务
4. 处理更重的推理

再升级到龙虾后端即可。

## 4. 架构分层

### 4.1 人格快速反应层

建议放在 Electron Main 主进程。

职责：

1. 读取当前角色状态
2. 读取短期记忆文件
3. 根据用户输入生成首句回复
4. 判断是否升级到后端龙虾
5. 给出 mood / affinity 提案
6. 对后端返回结果做最终人格化包装

它本质上不是完整 Agent，而是一个：

1. 轻量 LLM 驱动的 companion controller
2. 角色表达层
3. 升级决策层

### 4.2 龙虾后端能力层

当前主要是 `Nanobot`，未来可扩展到其他 `claw` 类框架。

职责：

1. 长期任务记忆
2. 工具调用
3. 搜索 / 文件操作 / 执行
4. 复杂推理
5. 后端原生工作流能力

这层应被视为：

1. 可替换的能力引擎
2. 更重的“深想”执行层

### 4.3 调度层

建议仍由主进程统一调度。

职责：

1. 维护 session / routeKey / agentId 隔离
2. 调用快速反应层
3. 根据升级判断决定是否调用龙虾
4. 将龙虾结果与人格层结果合并
5. 输出统一 conversation event

## 5. 短期记忆设计

### 5.1 设计原则

短期记忆不是完整长期记忆系统，而是滚动上下文缓存。

它的目标不是“永远记住一切”，而是：

1. 让轻量交互能够快速成立
2. 让人格连续性有即时支撑
3. 在不引入复杂基础设施的情况下提供自然上下文

### 5.2 存储形式

初期可以非常简单：

1. 一个文件即可
2. 每个会话/角色/路由一份

建议按以下维度隔离：

1. `agentId`
2. `backend`
3. `routeKey`
4. `sessionId`

这样与现有会话路由体系一致。

### 5.3 短期记忆建议内容

建议只存轻量内容：

1. 角色当前 mood / affinity 摘要
2. 用户称呼与偏好称谓
3. 最近若干轮交互压缩摘要
4. 最近 1 到 3 个关键事件
5. 最近一次升级给龙虾后得到的重要结论
6. 当前氛围或关系态标签

避免在短期记忆里塞：

1. 大段原始历史
2. 全量工具输出
3. 大量结构化工作记忆

### 5.4 自动压缩

短期记忆应该自动压缩，逻辑类似 Claude Code 的上下文压缩：

1. 新交互自然进入短期记忆
2. 当长度超过阈值时，自动生成摘要替换旧内容
3. 保留近期高价值内容，丢弃低价值细枝末节

压缩目标应优先保留：

1. 当前关系状态
2. 最近情绪变化原因
3. 最近形成的 shared context
4. 近期角色表达风格连续性

## 6. 升级到龙虾的判断

### 6.1 为什么必须有升级判断

快速反应层如果没有升级机制，就会被迫承担：

1. 更多记忆压力
2. 更多推理责任
3. 更多工具调用任务

这会很快把它变成第二个 Agent。

因此必须明确：

它的职责不是把所有问题都答好，而是：

1. 能快答时快答
2. 不确定时升级

### 6.2 建议升级条件

建议快速反应层在以下情况触发升级：

1. 用户请求明显需要工具
2. 用户请求属于复杂任务
3. 当前短期记忆不足以保证高质量回答
4. 用户要求回忆更早、更多、或更细的旧信息
5. 当前回答置信度不足

### 6.3 建议输出协议

快速反应层的 LLM 不要只返回一段文本，建议返回结构化结果，例如：

```json
{
  "reply": "当然呀，我先想想看。",
  "needsEscalation": true,
  "reason": "insufficient_context",
  "statUpdates": [
    { "stat": "mood", "delta": 1, "reason": "用户主动互动" }
  ]
}
```

这样主进程能稳定调度，也便于未来接别的 claw。

## 7. 一致性策略

### 7.1 不追求双记忆完全统一

当前方案不强求：

1. 壳层短期记忆
2. 龙虾后端长期记忆

在任何时刻完全一致。

这不是 bug，而是设计选择。

### 7.2 一致性如何自然形成

推荐策略：

1. 快速层先用短期记忆快速回复
2. 如果升级到龙虾，龙虾使用它自己的更强记忆进行处理
3. 龙虾返回的重要结论进入当前上下文
4. 主进程将该结论回写到短期记忆摘要中

这样即使之前短期摘要略有偏差，新的“想起来的内容”也能自然覆盖旧的浅层判断。

从用户体验上看，这更像：

1. 先凭直觉回应
2. 再认真想起更多细节

这种交互节奏本身是自然的。

## 8. LLM 配置策略

### 8.1 可以向用户隐藏“多层模型”的复杂度

当前项目对 `Nanobot` 的：

1. 部署
2. 进程生命周期
3. 配置

都已由软件本身管理。

因此快速反应层与龙虾后端，在部分支持的后端上，可以共享同一套 LLM 配置，对用户隐藏复杂度。

用户体验上更像：

1. 用户只配置一次模型
2. 软件内部自己决定如何使用它

### 8.2 为什么这在当前阶段是合理的

因为当前支持的 `claw` 类后端还很有限，尤其现在主要围绕 `Nanobot` 展开。

在这种情况下：

1. 优先降低用户理解成本
2. 优先降低配置复杂度
3. 优先把交互体验做顺

比提前暴露“多模型协作”的专业概念更重要。

## 9. 当前不建议做的事情

### 9.1 不建议立即实现完整 relationship memory infrastructure

当前不建议马上实现：

1. relationship memory store
2. 向量检索
3. 关系事件蒸馏器
4. 记忆投影器
5. 跨后端统一长期记忆 SoT

原因：

1. 复杂度大
2. 容易和后端龙虾的记忆系统冲突
3. 让“壳”逐渐膨胀成框架

### 9.2 不建议把龙虾长期记忆强行拉回主进程统一

这会导致：

1. 后端框架价值被削弱
2. 实现成本暴涨
3. 后端适配变得更重

## 10. 对当前仓库的落地建议

建议新增模块：

1. `desktop/electron/services/persona/fastPersonaService.js`
   - 人格快速回复
   - 升级判断
   - 数值提案

2. `desktop/electron/services/persona/shortTermMemoryStore.js`
   - 文件存储
   - 读取/写入
   - 自动压缩

3. `desktop/electron/services/persona/personaPromptBuilder.js`
   - 组装角色 prompt
   - 注入 mood / affinity / 短期摘要

4. `desktop/electron/services/persona/personaResponseRewriter.js`
   - 对龙虾输出做风格统一与角色化包装

5. `desktop/electron/services/chat/`
   - 在现有 conversation runtime 上接入升级调度

## 11. 建议实施顺序

### Phase 1

先实现最小闭环：

1. 短期记忆文件
2. 人格 prompt builder
3. 快速首句回复
4. 升级判断

### Phase 2

接入数值系统：

1. 从 `valueStateStore` 注入 mood / affinity
2. 让快速反应层给出 `statUpdates`

### Phase 3

接入龙虾返回后的风格包装：

1. 龙虾结果回到主进程
2. 输出统一为角色语气
3. 回写短期记忆

### Phase 4

再考虑更复杂能力：

1. 多 Agent 隔离
2. 多后端适配
3. 更细的摘要策略

## 12. 最终结论

在当前阶段，最推荐的方案不是：

1. 完整自建记忆框架
2. 或把一切都交给后端龙虾

而是：

1. 用一个轻量 `人格快速反应层` 承接角色感与低延迟体验
2. 用一个极简 `短期记忆文件` 提供滚动上下文
3. 让龙虾后端保留它自己的长期记忆与重能力
4. 不抢后端价值，只补足“壳”的灵魂

这版架构既符合当前项目“二次元龙虾壳”的定位，也给未来保留了足够的演进空间。
