# 多 Agent 隔离优先与像素空间打通方案

日期：2026-03-21  
最近更新：2026-03-21

## 背景与本次结论

本次讨论明确了产品优先级：

1. 必须先实现后端多 Agent 聊天隔离。
2. 隔离能力必须兼容未来多推理引擎并存（例如 OpenClaw 与 Nanobot）。
3. 每个 Agent 需要独立的 Live2D 配置。
4. 像素空间（Pixel Room）需要优先打通多 Agent 状态联动。
5. 桌宠多实例能力若实现成本过高，可后置，不作为当前阻塞项。

一句话目标：先把“多 Agent + 多引擎 + 会话隔离”的后端主干做对，再逐步扩到前端展示层。

## 当前状态（与目标的差距）

### 已具备

1. `officeState` 已支持 `activeAgentId + agents[]` 的多 Agent 结构。
2. Pixel Room 渲染层已支持多 occupant 展示。
3. 聊天运行时已支持基于 `sessionId` 的并发控制（`latest-wins`/`queue`）。

### 主要缺口

1. 聊天后端选择仍偏全局配置，尚未形成“按 Agent 路由”的稳定模型。
2. 事件协议中缺少稳定的 `agentId/backend/routeKey` 三元路由信息。
3. 前端聊天侧仍以单活跃流思路为主，无法完整表达多 Agent 并发会话。
4. Live2D 配置尚未作为 Agent 级配置统一建模。

## 范围与非范围

### 当前范围（必须）

1. 多 Agent 聊天隔离（上下文、并发、事件路由均隔离）。
2. 多推理引擎并存下的隔离（Agent 可绑定不同引擎）。
3. Agent 级 Live2D 配置建模与读取。
4. 像素空间按 Agent 实时展示状态。

### 非范围（后置）

1. 桌宠多实例窗口/多桌宠同屏交互完整方案。
2. 桌宠端复杂多 Agent 控件与布局编辑。

## 核心设计约束

1. 隔离维度不能只看 `sessionId`，必须引入 Agent 维度。
2. 任何聊天事件都必须能反查到唯一 Agent 与后端来源。
3. 引擎切换不能污染其他 Agent 的会话上下文。
4. 前后端协议要先向后兼容，再逐步淘汰旧字段。

## 目标架构（讨论共识）

### 1. 统一路由键

定义 `routeKey`：

`routeKey = agentId + backend + sessionNamespace`

说明：

1. 运行时并发控制基于 `routeKey`，而非仅 `sessionId`。
2. 同一 `sessionId` 只要 `agentId` 不同，也不会互相抢占。
3. 同一 Agent 在不同后端上的流也应隔离。

### 2. Agent Profile（配置中心）

为每个 Agent 建立独立配置，至少包含：

1. `agentId`
2. `displayName`
3. `chat.backend`（`nanobot` / `openclaw` / future）
4. `chat.backendConfigRef`（密钥与连接配置引用）
5. `live2d.modelPath` 与动作/表情预设
6. 可选 `office.sceneState` 初始偏好

### 3. 事件契约统一

聊天事件增加并稳定输出以下字段：

1. `agentId`
2. `backend`
3. `routeKey`
4. `sessionId`
5. `turnId`
6. 既有 `type/payload`

结果：

1. Pixel Room 可直接按 `agentId` 更新对应 occupant 状态。
2. 后续桌宠即使后置，也能复用同一事件协议。

### 4. 像素空间联动

1. `officeState` 作为多 Agent 展示总线继续保留。
2. 将聊天运行态（`writing/researching/executing/error/...`）按 `agentId` 写入 `officeState.agents[]`。
3. `activeAgentId` 仅表示当前主焦点，不影响其他 Agent 流处理。

## 分阶段执行计划

### Phase 0：后端隔离内核（最高优先）

1. 会话并发控制从 `sessionId` 升级为 `routeKey`。
2. `conversation:submit-user-text` 增加 `agentId/backend/profileId` 输入。
3. 主进程统一构建 `routeKey`，并在事件中回传。
4. 保持旧调用可用：未传 `agentId` 时默认 `main`。

### Phase 1：多引擎并存路由

1. 恢复/接入 OpenClaw adapter 到 backend manager（以 feature flag 或配置开关控制）。
2. 按 Agent Profile 选择后端，不再依赖单一全局 `chatBackend`。
3. 后端错误映射保留 `agentId/backend/routeKey` 上下文，方便定位。

### Phase 2：像素空间打通

1. 聊天事件驱动 `officeState` 的多 Agent 状态更新。
2. Pixel Room 展示多个 Agent 的实时状态与细节文本。
3. 完善 active agent 切换策略（仅焦点，不抢占其他流）。

### Phase 3：桌宠能力（后置）

1. 仅在前述能力稳定后再评估桌宠多实例或多角色同层。
2. 桌宠层优先复用既有 `agentId/routeKey` 协议，不单独造新模型。

## 验收标准（面向当前目标）

1. A Agent 与 B Agent 同时发起聊天，互不取消、互不串流。
2. A Agent 使用引擎 X，B Agent 使用引擎 Y，双方可并行工作。
3. 任一聊天事件都可定位到唯一 `agentId + backend + routeKey`。
4. Pixel Room 能同时正确展示多个 Agent 的业务状态。
5. 任一 Agent 的 Live2D 配置变更不影响其他 Agent。

## 风险与注意事项

1. 旧前端仍可能按单流消费事件，需要兼容期与灰度开关。
2. 设置项迁移要保证密钥存储兼容，避免破坏既有用户配置。
3. 多引擎并存后，错误与超时类型会更复杂，需统一诊断字段。

## 讨论纪要（本次确认）

1. 多 Agent 聊天隔离是刚性需求，不是可选优化。
2. 桌宠多实例不是当前前置条件，可以延后。
3. 像素空间因为已具备多 Agent 结构，应优先接入真实多 Agent 运行态。
4. 后续架构设计必须把“引擎可扩展”作为一等公民，而不是单后端特例。
