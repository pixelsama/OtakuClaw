# 像素空间意图与执行事实分层方案

日期：2026-03-23

## 1. 结论

采用“单一主导 + 事实回填”的分层模型：

1. 快速模型负责场景意图（`area + businessState`）决策。
2. 推理后端不参与意图决策，只上报执行事实（工具阶段状态）。
3. UI 展示由轻量 `state reducer` 计算 `effectiveState`，不是双模型仲裁系统。

该方案目标是：保留快速响应，同时避免双模型重复决策导致的冲突复杂度。

## 2. 背景与问题

当前像素空间是状态驱动位置：

1. `businessState -> area`
2. `area -> slots[]`
3. renderer 使用 `slot.x/slot.y` 渲染

在双层架构下，如果“快速模型”和“推理后端”都进行位置意图决策，会带来额外复杂度：

1. 优先级冲突（谁覆盖谁）。
2. 循环抖动（状态频繁切换）。
3. 实现复杂度大于收益（过度工程）。

## 3. 分层原则

### 3.1 快速模型：对话驱动预判

快速模型只做一件事：基于当前对话上下文给出“应该站在哪里、表现什么业务状态”的意图。

职责：

1. 输出 `scene-intent`（`areaId + businessState`）。
2. 覆盖闭合状态空间内的快速决策（`idle/writing/researching/executing/syncing/error`）。
3. 保障首响应体感。

### 3.2 推理后端：执行事实上报

推理后端只做一件事：上报自己正在发生的执行事实，不重复做场景意图推断。

职责：

1. 工具执行阶段上报 `agent-state`（如 `researching/executing`）。
2. 流结束上报 `done/error`。
3. 提供“地面真相”，而不是“预测意图”。

### 3.3 Runtime：轻量归约，不做复杂仲裁

Runtime 仅做稳定状态归约（reducer），不引入双模型决策竞争逻辑。

## 4. 事件契约（最小可用）

本方案与 RBEP 的关系：

1. 推理后端继续走 `RBEP v1`（`agent-state/text-delta/done/error`）。
2. 快速模型新增一条独立事件：`scene-intent`。
3. 两类事件进入同一个 `office state reducer` 得到 `effectiveState`。

### 4.1 scene-intent（快速模型 -> Runtime）

```json
{
  "type": "scene-intent",
  "source": "fast",
  "turnId": "turn_xxx",
  "agentId": "main",
  "intent": {
    "areaId": "desk",
    "businessState": "writing",
    "detail": "准备回复中",
    "ttlMs": 4000
  },
  "timestamp": "2026-03-23T10:00:00.000Z"
}
```

字段约束：

1. `areaId` 必须在场景配置 `areas` 内。
2. `businessState` 必须在允许集合内。
3. `ttlMs` 必填，避免意图长期占位（建议 2-6 秒）。

### 4.2 execution-fact（推理后端 -> Runtime）

沿用 RBEP 事件，不新增预测语义：

1. `agent-state`：执行阶段事实（例如工具调用）。
2. `done/error`：终态事实。

示例：

```json
{
  "eventType": "agent-state",
  "backend": "nanobot",
  "turnId": "turn_xxx",
  "payload": {
    "businessState": "executing",
    "detail": "Running a local command."
  }
}
```

## 5. Effective State 归约规则

每个 `agentId` 维护两份状态：

1. `intentState`（来自 fast）
2. `factState`（来自 backend）

渲染只看 `effectiveState`，规则固定：

1. 有 `factState` 时，`effectiveState = factState`。
2. 无 `factState` 且 `intentState` 未过期，`effectiveState = intentState`。
3. 无 `factState` 且 `intentState` 过期，`effectiveState = idle`（或上次稳定状态）。
4. 收到 `done/error` 后清理 `factState`，回落到 `intentState` 或 `idle`。

参考伪代码：

```js
function reduce(agent, event, now) {
  if (event.type === 'scene-intent') {
    agent.intentState = withExpire(event.intent, now + event.intent.ttlMs);
  }

  if (event.type === 'agent-state') {
    agent.factState = event.payload;
  }

  if (event.type === 'done' || event.type === 'error') {
    agent.factState = null;
  }

  const intentAlive = agent.intentState && agent.intentState.expiresAt > now;
  return agent.factState || (intentAlive ? agent.intentState : { businessState: 'idle' });
}
```

## 6. 为什么不需要“仲裁层”

该方案不是“两个决策器竞争同一语义”，而是“预测维度 + 事实维度”的串联：

1. 快速模型提供即时意图。
2. 推理后端提供执行事实。
3. reducer 做静态优先级归约（事实优先），不是策略仲裁。

因此复杂度是常量级，且可测。

## 7. 与现有代码的落地建议

Phase 1（最小改造）：

1. 在 `prepareTurn` 结束后发 `scene-intent`（当轮快速层输出）。
2. 现有 `agent-state` 事件继续沿用。
3. 在 office state 聚合处加入 `intentState/factState` 归约。

Phase 2（协议收敛）：

1. 将 `scene-intent` 纳入文档化事件定义（可命名为 `Office Intent Signal v1`）。
2. 保持 RBEP 只承载推理后端事实，不扩展成快速层协议。

Phase 3（多后端扩展）：

1. 新增 `nanoclaw` 时只需实现 RBEP 事实事件。
2. 快速层逻辑不因后端变化而改变。

## 8. 测试清单（必须覆盖）

1. 仅有 `scene-intent` 时，角色在 TTL 内按意图落位。
2. `agent-state` 到来后覆盖 `scene-intent` 展示。
3. `done/error` 后清除事实并正确回落。
4. 意图过期后自动回 `idle`。
5. 高频 `scene-intent` 不造成位置抖动（节流/去重）。
6. 多 agent 下 slot 分配稳定且不重叠。

## 9. 非目标

本方案不做以下能力：

1. 让快速模型输出任意绝对坐标 `x/y`。
2. 让推理后端做场景意图预测。
3. 引入复杂冲突仲裁策略引擎。
